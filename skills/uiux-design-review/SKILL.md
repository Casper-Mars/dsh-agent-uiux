# 设计评审：把「看着不错」变成「逐条可查」

评审不是表达喜好，而是按固定维度逐条判定，产出**可执行**的修改清单：
哪一屏、哪个状态、为什么不行、怎么改。

打分 rubric 见 `references/rubric.md`；无障碍检查见 `references/accessibility.md`；
报告模板见 `assets/review-report.md`。

## 五个维度

1. **结构**：信息层级清楚吗？主操作唯一且醒目？栅格对齐？
2. **token 合规**：有没有裸 hex / px？语义命名还是颜色名？
3. **状态覆盖**：default / empty / loading / error / disabled / focus 是否齐全？
4. **可访问性**：对比度、焦点可见、可点击区域、语义标签。
5. **反 AI-slop**：字体是否默认货、是否白底紫渐变、层次是否只靠颜色。

## 评分

- 每个维度 0–2 分（0 不通过 / 1 勉强 / 2 通过），总分 10。
- 任一维度 0 分 → 整体不通过，必须修。
- 2 是「能上线」，不是「完美」。诚实打分，不报喜。

## 输出

按 `assets/review-report.md` 产出：结论（通过 / 需修改）、分维度得分、
逐条问题（含定位与建议）、必改 vs 可选。

## 判据

- 每条问题都要指到具体屏/状态/文件。
- 「我觉得不好看」不算问题；「这屏主操作与次要操作等权，用户找不到下一步」才算。
- 偏差回设计卡修，不在评审里直接改实现。

## 反合理化

| 借口 | 现实 |
|---|---|
| 整体看着挺好，给通过 | 逐条过 rubric，漏一个状态就是漏一个 bug |
| 这个对比度差一点没关系 | 差一点就是不合格，数值说明问题 |
| 评审就是挑刺 | 评审是防返工，放过问题成本更高 |
| 实现和设计差一点点正常 | 没有 design_ref 对不上的实现，等于没验收 |
